# LitGraph：论文处理、RAG、节点与关系的完整说明

本文区分**当前代码实现**与**大规模扩展建议**。研究空间的检索索引和画布的布局向量是不同用途的数据，不能混为一谈。

## 1. 本次研究空间的实际流程

```text
用户问题 + 当前论文范围 + 最近的用户问题
       │
       ├─ 简单概念：本地词汇扩展（无额外模型调用）
       └─ 精确事实 / 比较 / 专家：精简检索规划（最多等待 16 秒）
            ├─ 聚焦实际所问事实，标题用于限定来源范围
            └─ 2–3 条补充查询、具体词项与目标章节
       │
本地 MD ─ 段落/句子分块 ─ 标题、作者、年份、章节、页码、行号
       │
       ├─ BM25 关键词检索
       └─ multilingual-e5-small 多语言稠密向量检索
                 │
          多查询结果按 chunk 身份合并（RRF）
                 │
          轻量特征重排 + 明确目标论文之间的覆盖
                 │
          基础预算 + 一轮限量本地补检 + 上下文总长度约束
                 │
          原文证据 → 模型回答 → 校验证据编号 → 显示页码/行号
```

借鉴了 [LightRAG 的关键词提取与多路径检索实现](https://github.com/HKUDS/LightRAG/blob/main/lightrag/operate.py)的双层关键词、结果合并、来源追踪和缓存思想。本产品没有移植其整套服务，也没有把当前画布改成 LightRAG 的实体—关系知识图谱；两个层次的关键词都参与本地片段搜索，而不是声称已经存在独立的实体库和关系库。

### 文档分块

`src/research-evidence.js` 以空行、章节标题和 PDF 页边界分组。通常保留原段；过长段落优先在句号、问号、分号等边界拆分，约 1,400 字符封顶。没有可识别句界时才退回换行、空格边界，极端无空白长串才按长度拆开。它是结构/句界感知的分块，不是额外调用 LLM 逐段判断主题转换，也不保证修复错误的 PDF 阅读顺序。

每个 chunk 保存：稳定 ID、论文 ID、标题、作者、年份、DOI、章节类型、最近章节标题、PDF 文件页、MD 起止行、原文字符偏移、内容哈希、分块版本、来源类型。无法识别章节时标记 `unknown`；没有 PDF 页标记时只给 MD 行号，绝不猜测出版社印刷页码。页间段落可能被分开，但不会用不存在的页码补齐。

保存 MD 时，本地服务同时生成 `data/chunks/<文档标识>.json`。旧文档无需重新分析才能检索：查询时根据当前 MD 生成同版本片段。当前查询仍在内存中组织候选，不是已经完成磁盘倒排数据库改造。

### 查询与混合检索

改写模型只生成检索词和问题，不允许猜测答案中的人数、效应量或结论方向。原始提问用于确定来源范围，去掉冗长标题后的问题仍作为检索查询保留。标题或 DOI 在原问题中明确出现时，先定位对应论文；未明确指定时在当前选择的论文范围内搜索。改写结果不能随意把候选范围扩展到其他项目。

稠密向量使用本地量化的 [multilingual-e5-small](https://huggingface.co/Xenova/multilingual-e5-small)，384 维，采用 `query:` / `passage:` 前缀、均值池化及归一化。模型及推理资源在本地提供，不将论文发送给 embedding 网站。生成回答和改写仍使用用户配置的 API 或外部 Agent。

关键词路径使用 BM25；各改写问题都参与检索。合并采用 reciprocal rank fusion，避免直接相加不可比的原始分数。后续重排综合合并排名、关键词匹配、向量相似度、目标章节，并降低参考文献页和极短片段的权重。**这是透明的特征重排，不是训练过的 cross-encoder reranker。**

比较题给原问题明确指定的论文分配片段，不强制给全部论文各塞一个短片段，最终保留完整 chunk。1.2.6 的快速精确问题基础预算为 20 段/28,000 字符，专家为 24 段/42,000 字符；简单概念问题为单篇 6 段/8,000 字符、多篇 12 段/12,000 字符。一轮本地补检针对问题维度及匹配的摘要/开头原文，最多增加 6 段/8,400 字符，总上限 48,000 字符，不额外调用模型、不现场建立段落向量，也不宣称覆盖穷尽。未明确指定标题时，整个选定论文库参加检索；明确指定标题/DOI 时尊重该论文范围。

12 道开发题（8 道单篇、4 道比较，使用不同于正式测试的事实）上的预设选择规则为：在相同预算下，选达到最高参考证据召回的最小 k。

| k | 开发题证据找回 | 平均正文字符 |
|---:|---:|---:|
| 8 | 15/16 | 9,013 |
| 12 | 15/16 | 13,230 |
| **20** | **16/16** | **22,107** |
| 32 | 16/16 | 27,373 |
| 48 | 16/16 | 27,368 |

开发题和正式题共用固定语料，但不共用所问事实；它不是按论文独立划分的泛化验证。

### 引用与故障

模型在事实后输出 `[E1]` 等本次证据编号。软件验证编号存在，并依据实际元数据补上论文、章节、PDF 文件页和 MD 行号。编号有效不等于已证明每个学术解释正确：引用蕴含关系仍需审阅。模型推断继续使用 `【AI 推断】` / `[AI inference]` 标记。

改写或 embedding 失败时降级到可用路径，并在界面提示；评测中的稠密路径失败会被单列，不能当作完整混合检索成功。原文缺失、OCR 乱码、仅有摘要的情况仍必须说明。

## 2. 新增论文怎样更新

1. 为论文创建项目内节点及元数据，先保存 PDF 原始字节。无全文时节点仍可存在，但不声称有原文。
2. 提取可读文字，按页保存 MD；扫描件或严重编码错误会保留原文并要求 OCR，不虚构正文。
3. 保存 MD 时写入该论文的 chunk 文件。原文更换后使用新内容哈希，不沿用旧片段身份。
4. 查询首次需要这些片段时生成其稠密向量。向量缓存键包括模型版本、池化/量化设定、输入文本和 query/passage 类型；相同内容复用缓存，变化的内容重新编码。不需要因加一篇论文重新向量化全部旧论文。
5. 稠密向量在本机独立 CPU 工作进程计算，缓存写入数据文件夹的 `vectors/rag`，不占用界面线程。浏览器预览通过受本机同源令牌保护的服务调用同一实现。查询计划在会话内缓存，身份包含模型配置、问题、范围和历史；没有跨用户共享。旧缓存不是检索候选目录，已删除节点不会仅因缓存残留重新进入检索。
6. 原文分析生成总结、关键词、短观点标签及主题类别。与最多六篇已有、可读且标题较相关的论文片段比较，验证两端引句后写入支持/反对/相关关系。**这并不保证发现新论文与全部旧论文之间的所有关系。**
7. 引用标识匹配后补充引用边。保存项目和分析状态，刷新图谱并重新布局。已有来源文件不因重排画布而被删除。

当前仍有两个整体步骤：查询 BM25 的词频统计会按当前候选重新组织；画布标题/摘要 TF-IDF 布局向量可能全量重算。不能把整个产品描述成已经全面增量化。

## 3. 一篇论文在后台实际存什么

```text
Paper A（一个画布论文节点）
├─ Metadata：id、title、authors、year、DOI、journal
├─ Source：PDF 路径、MD 路径、可读性、处理状态
├─ Chunks：正文 + 章节 + 页码/行号 + 内容哈希
├─ Retrieval vectors：正文 chunk 的多语言稠密向量缓存
├─ Analysis：summary、claimLabel、keywords、primaryTheory
├─ Evidence relations：目标论文、关系、理由、两端原文引句、校验状态
├─ Citation metadata：被引量、参考 DOI / OpenAlex IDs
└─ Layout：坐标、颜色、大小、布局所需向量/力参数
```

用户提出的 Topics、Method、Population、Measures、Findings、Limitations 结构很适合作为下一阶段的标准化论文证据层，但**当前并未将这些字段全部提取为独立、经过验证的实体表**：关键词可以覆盖部分 Topics；方法、人群、指标、发现和局限主要保存在 MD 与总结中。不能把总结里提到某方法等同于已经有可查询的结构化 Method 实体。

例如样例中的 *Enhanced Avoidance Habits in Obsessive-Compulsive Disorder*，原文可以支持“25 名 OCD 患者、25 名对照、电击回避任务、过度训练、结果贬值”等事实。当前它们进入原文片段和总结。若扩展成细粒度结构，应为每个事实分别保存 `value + evidenceChunkIds + sourceQuote + extractionStatus`，而不只保存一个没有出处的标签。发现还应保留条件、对照、方向、效应量及不确定性；没有报告的字段为空，不能补猜。

## 4. 画布节点、颜色、大小与三种关系

**节点**是一篇被导入的论文记录，不是模型凭空创造的概念。导入元数据即可先出现节点；下载、转换和分析分别补全其状态。样例有一个重复节点，评测主结果已去重处理。

**颜色**来自 `primaryTheory` 对应类别的颜色，并结合归属强度/显示参数混色。颜色深浅不是校准过的科研置信概率。**大小**来自来源元数据的被引量或已有引用百分位，经对数/幂变换再乘用户大小设置；不是从 PDF 的文件大小或引用列表长度猜被引量。没有可靠被引记录时应按未知处理。

| 关系类型 | 实际生成依据 | 不代表什么 |
|---|---|---|
| 引用边 | 本篇真实参考 DOI / OpenAlex referenced_works 与项目内目标匹配 | 不代表支持目标结论，也不等于本篇被引次数 |
| 支持 / 反对 / 相关边 | AI 比较两篇原文片段，返回关系和两端原文引句；软件逐端匹配引句 | 字面匹配不是自动同行评议，不能证明推断一定正确 |
| 语义布局相似边 | 当前画布仍用标题/摘要 TF-IDF 余弦相似度，每篇取最多 5 个邻居并去重 | 不是本次新增的正文 E5 向量，也不是支持/反对或真实引用 |

因此“Concept overlap 高、Method similarity 中、Finding direction 一致”**不是目前代码里已有的一套统一数值算法**。即使以后添加，也要拆开：概念重合只是候选召回；同名任务不保证设计相同；方向一致需对齐同一指标、条件、对照和效应定义。相关性高不能直接生成支持边，方向相反也不一定是学术矛盾。

## 5. 当前理论聚类算法是什么

分析模型根据原文片段复用已有类别，或提出新的有意义类别；节点保存 `primaryTheory`。二维布局给每个类别一个中心点，再由边的吸引、节点斥力、碰撞避免与中心力共同决定位置；年份树额外固定年份方向。当前类别不是 Leiden/Louvain 或 K-means 自动发现的社区，不应宣传为这些算法。D3 多体力使用空间近似来降低力计算成本，参见 [D3 官方说明](https://d3js.org/d3-force/many-body)。

分类也不意味着经严格学术定义验证的“理论”：项目中的有些类别实质是主题领域或研究维度。类别的名称、合并和学术意义仍应由用户检查。

## 6. 几千篇、十万篇怎样做

**当前版本没有通过几千篇或十万篇压力测试，也没有完成十万篇级架构。** 本次 50 篇的质量结果不能证明那个规模的速度和稳定性。尤其当前候选扫描、全量文档加载、TF-IDF 两两相似度及全图布局都会成为瓶颈。

扩展建议如下，尚非本轮已交付功能：

| 层 | 几千篇到十万篇应采用的设计 |
|---|---|
| 原文处理 | 磁盘持久队列，逐篇事务、版本/哈希、断点恢复；PDF/OCR 与问答分离 |
| 索引 | 磁盘倒排索引 + HNSW 等近似向量索引；按项目、论文、章节做过滤索引 |
| 查询 | 先筛选目标范围，再多路取有限候选；重排几十至数百个候选，最终仅发送几十个证据片段 |
| 关系生成 | 新论文先召回有限候选邻居，再比较原文；不让 LLM 对全部论文两两比较 |
| 大图显示 | 默认显示主题/社区聚合图，逐层展开局部子图；离线布局、分块加载和视口裁剪 |
| 主题维护 | 规范化类别或离线社区发现，增量分配新论文；保存类别变更和来源，不每次问答重新聚类 |

[Qdrant 官方索引文档](https://qdrant.tech/documentation/manage-data/indexing/)展示了向量索引与元数据过滤索引配合的方式；这是可选扩展方向，当前产品没有依赖运行中的 Qdrant 服务。

以**假设**每篇 100 个 chunk 估算，十万篇是 1,000 万个 chunk；384 维 float32 原始向量约 15.36 GB，还没计图索引、正文、元数据及备份。论文两两比较有约 50 亿对，不能逐对调用模型。实际文档长短、设备、OCR 比例、模型并发和网络差别很大，不能承诺固定处理时间。

首次建库可能需要长时间后台处理；建完索引后的问答不应随论文数线性地把全部原文发给 AI。粗略总耗时可分为：PDF/OCR、分块/向量化、论文分析/有限关系比较三个批处理阶段；在线耗时则是查询改写、索引查找、重排和回答生成。应分别测吞吐、P50/P95、内存与磁盘，而不是只报一次回答的平均秒数。

## 7. 响应时间优化的实际边界

已采用本地量化模型、模型实例复用、去重批量编码、内容级向量缓存、查询计划缓存、后台 worker 和有限 top-k。样例安装资源额外包含与原文内容及模型版本绑定的预计算段落向量（不是缓存答案），避免首次问题触发整库编码。快速概念问题不额外调用模型改写；精确数据、比较、上下文追问及专家模式保留改写。消息记录分阶段用时，不承诺外部模型的固定返回时间。

同一单篇浏览器验证中，初版 WASM 首次检索约 59.45 秒；改为本机 CPU 工作进程后约 9.64 秒，紧接着的相同检索约 22 毫秒。这仅是该篇论文的两次本机集成验证，不是全项目在线问答的 SLA。75 题正式运行的全流程中位数为 37.67 秒，其中改写中位数 15.92 秒、检索 6.91 秒、回答生成 14.12 秒；分项中位数不能直接相加。

代码入口：`research-evidence.js`（分块/位置）、`research-query.js`（计划）、`research-hybrid.js`（混合及重排）、`research-embedding.js`（模型与缓存）、`research-worker.js`（网页后台执行）、`research-agent.js`（回答规范）、`main.js`（分析、图关系与界面整合）。
